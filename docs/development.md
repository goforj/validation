# Development

The repository has one runtime module and a separate documentation tooling module. Neither has external Go dependencies. Go 1.24 is the minimum language version. Coverage reporting also uses Python 3 and its standard library. Use a current patched supported toolchain for vulnerability scanning.

The executable programs under examples are the source of truth for workflows and expected output. Their snippet markers drive the README generator; GoDoc owns API descriptions. Edit docs/README.tmpl for surrounding prose and layout. Never fix only the generated README.

Keep example statements within roughly 60 visible columns for GitHub's narrower README panes. Use vertical chains for longer rule sequences and blank lines between setup, validation, and output. Keep independent demonstrations in separate snippets so the generator renders separate code blocks. Show only the setup needed to understand an operation; the complete program supplies the rest. Expected output stays immediately after the producing call.

Currency identifiers and fluent selectors are generated by scripts/currencies.py from the pinned codes-only snapshot in testdata/currency-codes.txt. Regeneration is offline. Update the authoritative list and provenance when adding identifiers, preserve existing exported codes, and run make generate. The parity check regenerates both the currency source and README twice.

Run the standard checks from the repository root:

```sh
make test
make test-race
make vet
make tidy
make modules-check
make test-coverage
make generate
make check-generated
make security
make verify-consumer
```

Unit coverage requires every instrumented statement to execute. The coverage command merges ordinary tests with instrumented example subprocesses. Race runs pass race instrumentation to those subprocesses. Coverage profiles and raw test JSON stay under .artifacts and are not committed as fresh evidence from an earlier source revision.

The committed quality report records its source fingerprint, toolchain, and platform. CI regenerates that report for its own execution; cross-platform byte parity applies to README and badges rather than the report's execution provenance. Both runs independently require exact statement coverage.

Public-consumer verification needs network access and a pushed revision. It first resolves HEAD to a canonical version using a separate metadata cache, allowing GitHub lookup when the public proxy caches a failed commit lookup. It then installs that version through the public Go proxy and checksum database in a different fresh module cache, rejects local replacements or version mismatches, and runs the packaged library tests and executes all canonical example programs outside the checkout. The installation itself never falls back to a direct source download. To verify another published revision, run `./scripts/verify-consumer.sh <revision>`. On pushes to main, CI runs this check on both the minimum Go line and stable Go. Pull requests run the local checks without requiring their unpublished merge commits to resolve through the public proxy.

No external services or credentials are required for tests. The context-aware example returns a deterministic dependency failure and does not claim to contact a provider. Drivers and framework integration are outside this utility library's scope.

CI checks the minimum Go line and stable Go, both modules, formatting, unit coverage, race behavior, vet, module inventory, tidy parity, and generated parity. The Security workflow uses a pinned govulncheck version on stable Go. Codecov project and patch checks require exact unit coverage, with upload failures treated as failures. Hosted app configuration is separate from these source files.

Runtime releases use root version tags such as v0.2.0. Each version must resolve through the public Go proxy with normal checksums and GOWORK=off before publication is reported as complete.

Only the root module is a runtime release target. The docs module is repository tooling and does not need a separate release tag. Review [release readiness](release-readiness.md) before selecting and publishing a version.
